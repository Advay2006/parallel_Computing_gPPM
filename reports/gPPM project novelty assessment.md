# GPU port carries the project's real novelty

The project is mostly a careful reimplementation, and its genuinely new parts are narrow but defensible. **No published GPU decoder for SD, PMDS, STAIR or LRC codes was found, and no GPU port of PPM/gPPM exists.** gPPM's authors explicitly chose CPU multithreading over GPUs, so the CUDA decoder and the CPU-vs-GPU comparison across GF(2^8/16/32) are the strongest novelty claims. Reading the full gPPM paper (local copy) settles the four questions the literature search left open. gPPM **already uses SIMD** (ISA-L and GF-Complete). It **leaves the dependent remainder serial**. It **defines the weight c in C = u + c·v but never says how c is set or what value it takes**. It ran on **4–8-core Sandy Bridge-era Xeons/i7s with SSE4.2, at most 4 threads and 32 MB stripes**. So the SIMD kernels are not new relative to gPPM. The OpenMP independent groups are a direct reproduction. The byte-range-parallel remainder and the timed calibration of c are small but real extensions of the gPPM algorithm, built from well-known techniques (data-parallel region splitting; Zhou & Tian's measured operation weights). The CPU/GPU result, where the GPU wins only GF(2^32) at 32 MiB, agrees with the best-controlled prior comparisons. It also carries a confound the student must disclose: the CPU's GF(2^32) kernel is unusually weak, so part of the GPU's "win" is a slow CPU baseline. Absence claims rest on Semantic Scholar/OpenAlex citer lists and targeted web searches. Google Scholar and Chinese-language venues were not checked.

## gPPM's full text settles four open questions

The research notes flagged one item as "the single most important" to verify: what gPPM itself already does. The local PDF of Li et al. (ACM TACO 20(4), Art. 51, 2023) answers each question directly ([gPPM, DOI 10.1145/3625005](https://doi.org/10.1145/3625005); read from `docs/pc project paper.pdf`).

| Open question | What gPPM's full text says | Consequence for the project |
|---|---|---|
| Does gPPM multithread the dependent remainder? | No. Algorithm 1, Step 3: "Once the T threads used to decode the p independent sub-matrices … are finished, we decode the remaining sub-matrix H_rest." §4.2: "the parallel optimization of the gPPM algorithm is the same as that of the PPM algorithm." §5.2 attributes sub-linear thread scaling to the parallel part being "a small proportion" of decoding. | The byte-range-parallel remainder is an extension to gPPM that gPPM's own scaling discussion motivates. |
| Does gPPM use SIMD kernels? | Yes. §5.1: "All experiments employ Intel's SIMD instruction to accelerate the decoding performance [3, 42]", where [3] is ISA-L and [42] is Plank/Greenan/Miller FAST'13 (GF-Complete). Without SIMD, speeds were "only a few tens of MB/s". | SIMD in a PPM decoder is not new. The student's SSSE3/AVX2 kernels are a from-scratch reimplementation. |
| How is c in C = u + c·v set? | §4.1 introduces C = u + c·v, "where c is the coefficient of the multiply operation relative to the addition operation." No numeric value, measurement procedure or tuning method appears anywhere in the paper; a search of the full text finds c only in this definition and the notation table. | gPPM leaves c unspecified. Measuring it on the host fills a real gap, not merely "tuning a published constant." |
| What hardware and parallelism? | Intel E5-2603 (4 cores, 1.8 GHz), i7-3930K (6 cores) and E5-2650 (8 cores), all SSE4.2. T ≤ min{4, cores}. Mostly 32 MB stripes, 10 runs per decode, GF(2^8/16/32) switched per configuration. Built on Plank's open-source SD decoder [40]. No GPU. | The student's setup (Core Ultra 9 185H, AVX2, up to 8 threads, RTX 4050) is new hardware territory, but the workload shape (32 MB stripes, n = r = 16, z = 1, Plank's coefficients) deliberately mirrors gPPM. |

gPPM's related-work section also says why there is no GPU: "Researchers [16] also use general-purpose GPUs … but our implementation uses multi-threading instead, which is more general and does not introduce additional cost" ([gPPM §6](https://doi.org/10.1145/3625005)). Reference [16] is Haddock et al., SpringSim 2019, the Gibraltar large-stripe work. The original authors therefore considered GPUs and declined them, which makes the student's GPU port an explicit test of a design choice gPPM left untested.

Two details of gPPM's selection logic matter for the viva. First, gPPM's PPM path fixes matrix-first for independent groups and normal for the remainder (Algorithm 1). Its gPPM extension evaluates Min(C(F⁻¹S), C(F⁻¹+S)) per sub-matrix and only once for all identical independent groups, then compares against whole-matrix sequences (Algorithm 2). The student's decoder, which "sums the cheaper sequence estimate for each independent group and the remainder" and partitions only when cheaper, is a faithful reproduction of Algorithm 2, not an extension. Second, gPPM motivates c with measured RS throughput (e.g., RS(15,2): 3387 MB/s normal vs 2837 MB/s matrix-first) but never closes the loop by deriving c from those measurements.

## SIMD kernels and parallel groups reproduce known techniques

The SIMD layer (contribution 1) is the least novel part of the project. The **SSSE3 PSHUFB nibble-table GF(2^8) kernel is the textbook technique**. It appears in Anvin's RAID-6 work, GF-Complete, ISA-L and klauspost/reedsolomon ([GF-Complete TR UT-CS-13-717](https://web.eecs.utk.edu/~jplank/plank/papers/UT-CS-13-717.pdf); [intel/isa-l](https://github.com/intel/isa-l); [klauspost/reedsolomon](https://github.com/klauspost/reedsolomon)). The GF(2^32) design, with four 256-entry tables built at the start of each region call and four lookups plus XORs per word, is GF-Complete's "lazy SPLIT 8,32" almost verbatim. The GF-Complete report states that it "requires four 256-element tables which must be created at the beginning of the multiply_region() operation" ([UT-CS-13-717 §8.3](https://web.eecs.utk.edu/~jplank/plank/papers/UT-CS-13-717.pdf)). Runtime dispatch with a scalar fallback is standard in ISA-L's multibinary dispatcher and Linux's boot-time RAID-6 selection ([Linux lib/raid6/algos.c](https://github.com/torvalds/linux/blob/v6.6/lib/raid6/algos.c)).

The only new element is **using AVX2 `vpgatherdd` for the GF(2^16)/GF(2^32) lookups**, and the evidence suggests it is a regression, not an advance. GF-Complete found shuffle-based SPLIT-TABLE with ALTMAP layout fastest "for every value of w" ([UT-CS-13-717](https://web.eecs.utk.edu/~jplank/plank/papers/UT-CS-13-717.pdf)), and its source has no AVX2 or gather path ([ceph/gf-complete gf_w32.c](https://raw.githubusercontent.com/ceph/gf-complete/master/src/gf_w32.c)). General benchmarks found AVX2 gather no faster than scalar loads ([Johnny's SW Lab](https://johnnysswlab.com/?p=2014)). The 2023 Downfall/GDS microcode mitigation specifically slows gathers ([Red Hat GDS advisory](https://access.redhat.com/solutions/7027704)). The student's Callgrind finding, that the scalar field-multiply routine accounts for **58.2% of GF(2^32) instructions because tables are rebuilt on every region call**, reproduces the amortization problem GF-Complete documents. GF-Complete already solves it with a one-entry `last_value` cache ([gf_w32.c](https://raw.githubusercontent.com/ceph/gf-complete/master/src/gf_w32.c)), and ISA-L solves it by precomputing all per-coefficient tables once via `ec_init_tables` ([erasure_code.h](https://raw.githubusercontent.com/intel/isa-l/master/include/erasure_code.h)). The profile is a useful diagnostic, but the remedy is known prior art.

For contribution 2, **OpenMP over independent groups is PPM's core idea**. PPM (ICPP 2015) "parallelizes the encoding/decoding operations" over the partitioned matrix ([dblp](https://dblp.dagstuhl.de/rec/conf/icpp/LiCWZXHS15.html)), and gPPM's Algorithm 1 assigns sub-matrix p to "thread (p mod T)" ([gPPM](https://doi.org/10.1145/3625005)). The **byte-range-parallel remainder** is different: gPPM explicitly serializes it, and no indexed citer of PPM or gPPM parallelizes it ([Semantic Scholar citers of gPPM](https://api.semanticscholar.org/graph/v1/paper/aa8d1fc05ec4034cac17b0c2d54518db83774f39/citations?fields=title,authors,venue,year,externalIds&limit=100)). The technique itself is generic. Splitting GF region operations across threads by data range is how multithreaded Jerasure, Founsure and every GPU coder parallelize, because GF region arithmetic is bytewise independent ([OpenMP/pthreads Jerasure 2.0](https://www.researchgate.net/publication/321018556_OpenMP_and_POSIX_threads_Implementation_of_Jerasure_20_Erasure_Coding_Library); [Founsure](https://arxiv.org/pdf/1702.07409)). The honest framing is "applying standard data-parallel splitting to the Amdahl bottleneck that gPPM leaves serial." The student's measured **1.20–1.86× gain from parallel remainder over L2 at T = 8** is the evidence that makes this extension worth reporting.

## Measuring c fills a gap gPPM left open

The calibrated cost weight (contribution 3) is more novel than the notes assumed, because gPPM never specifies c. The student's decoder times coefficient-one and coefficient-two region operations on 256 KiB regions per field and build, then sets c = (multiply-XOR time / XOR time) − 1, clamped at zero. The GPU variants use sixteen interleaved probe pairs on 32,768 symbols. No PPM/gPPM citer does anything comparable ([Semantic Scholar](https://api.semanticscholar.org/graph/v1/paper/aa8d1fc05ec4034cac17b0c2d54518db83774f39/citations?fields=title,authors,venue,year,externalIds&limit=100); [OpenAlex](https://api.openalex.org/works/doi:10.1145/3625005)).

The *method* has clear precedent, though. Zhou & Tian (FAST'19) set the XOR-vs-copy weight in their erasure-coding cost function "according to the empirical testing result of these operation on the target workstation". They measured about 1.5× and found the calibrated cost best predicted throughput, with 0–10% gains ([Zhou & Tian FAST'19 §4.3](https://www.usenix.org/system/files/fast19-zhou.pdf)). Boot-time timing to choose kernels is decades old in Linux RAID-6 and XOR code ([crypto/xor.c](https://github.com/torvalds/linux/blob/v6.6/crypto/xor.c)). The defensible claim is therefore "first measured instantiation of gPPM's unspecified c, per field and per backend," not "first hardware-calibrated erasure-coding cost model."

There is also a caveat the student should state before an examiner raises it. A measured c captures the project's own kernel quality. On GF(2^32), where 58% of instructions go to table rebuilding, c is inflated by an implementation artifact, and a better kernel would shrink c and could flip sequence choices. A further subtlety: the student's c = ratio − 1 is the right reading if u already counts every nonzero (so non-one entries pay 1 + c). gPPM's wording, "coefficient of the multiply operation relative to the addition operation," is ambiguous between the ratio and the excess. The paper should state its interpretation explicitly. The student's evaluation does not yet show that calibration changes a selection decision or improves accuracy relative to a fixed c, and that is the experiment that would turn this from a mechanism into a result.

## No SD or gPPM decoder has run on a GPU before

The CUDA decoder (contribution 4) is the most defensible novelty claim at the *system* level, and the least novel at the *kernel* level. GPU erasure coding for plain RS and Cauchy RS is mature. Examples are Gibraltar (Curry et al., 2008–2011), PErasure (ICC 2015, about 10× multithreaded Jerasure), G-CRS (TPDS 2018, up to 3× PErasure), the OpenCL heterogeneous study (ASAP 2016) and ECS2 (CLUSTER 2020) ([PErasure](https://www.comp.hkbu.edu.hk/~chxw/papers/icc_2015.pdf); [G-CRS](https://www.comp.hkbu.edu.hk/~chxw/papers/G-CRS.pdf); [ASAP'16](https://hzhou.wordpress.ncsu.edu/files/2022/12/asap16.pdf); [ECS2](https://www.computer.org/csdl/proceedings-article/cluster/2020/667700a349/1oqKEKFMFNK)). All of them target MDS RS/CRS, almost all over GF(2^8) or w ≤ 8 bitmatrices ([EC-Bench](https://par.nsf.gov//servlets/purl/10112763)). Targeted searches for GPU decoding of SD, PMDS, STAIR or LRC codes returned only coding-theory constructions, and the 2024 TOS erasure-coding survey lists no such system ([TOS 2024 survey](https://keyuncheng.github.io/files/publications/tos24ecsurvey.pdf)). Plank's SD reference decoder is serial ([UT-CS-13-704](https://web.eecs.utk.edu/~jplank/plank/papers/CS-13-704.html)). The only hardware-parallel gPPM citer, FPGA-ECDR (Cluster Computing 2024), targets Cauchy RS on an FPGA ([OpenAlex](https://api.openalex.org/works/doi:10.1007%2FS10586-024-04401-X)).

The kernel design choices themselves are standard. **One thread per output byte** is ASAP'16's baseline mapping, and that paper already compared shift-and-reduce, log/exp and full-table GF(2^8) multiplication on a GPU, finding Russian-peasant slowest ([ASAP'16](https://hzhou.wordpress.ncsu.edu/files/2022/12/asap16.pdf)). Host-side matrix preparation with device-side application appears in GPU-RSCode and a USPTO patent ([GPU-RSCode](https://yszheda.github.io/GPU-RSCode); [USPTO 10230398](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10230398)). CUDA streams for concurrent independent coding tasks date to Gibraltar's SC12 asynchrony study ([SC12](https://dblp.org/rec/conf/sc/ZhouSC12a)). Mapping *gPPM's independent row groups* to separate streams, with a cost-model-driven host selector choosing one or two kernel launches per product, is a specific new combination rather than a new technique. One finding is mildly interesting against prior art: the student's GF(2^16) table variant was *slower* than direct arithmetic, the opposite of ASAP'16's GF(2^8) result. That fits a 128 KiB log/antilog table spilling out of fast on-chip memory, though the student has no occupancy or cache counters to confirm it.

## The GPU's narrow win matches fair-baseline studies

The CPU-vs-GPU comparison (contribution 5) confirms the literature rather than contradicting it, and its field-width axis looks new. Headline GPU speedups in prior work mostly rest on weak baselines. Examples are single-core ISA-L in the SC17 Gibraltar poster, and single-thread or non-SIMD Jerasure in PErasure and GPU-RSCode ([SC17 poster](https://sc17.supercomputing.org/SC17%20Archive/tech_poster/poster_files/post207s2-file2.pdf); [GPU-RSCode](https://yszheda.github.io/GPU-RSCode)). Against multithreaded SIMD ISA-L on a 28-core Xeon, ASAP'16's K40m won by only **about 1.38× end-to-end with 8-stream overlap**, and lost without overlap (2.15 vs 2.83 GB/s) ([ASAP'16](https://hzhou.wordpress.ncsu.edu/files/2022/12/asap16.pdf)). EC-Bench concluded that "highly optimized onload coders (e.g., Intel ISA-L) outperform offload coders for most configurations" ([EC-Bench](https://par.nsf.gov//servlets/purl/10112763)). The student's **1.25–1.39× GF(2^32) win at 32 MiB, with losses for GF(2^8)/GF(2^16) and at 128 MiB**, sits squarely in that band.

No prior paper sweeps field width w = 8/16/32 on GPU versus SIMD CPU, so the observation that the GPU helps only at the widest field appears new as an empirical result. The student must present it with the confound attached. The CPU's GF(2^32) path is its weakest kernel: L2 SIMD improved GF(2^32) only 1.07–1.26× over scalar, versus up to 9.85× for GF(2^8), and 58% of its instructions are table rebuilds. A GF-Complete-style SPLIT 4,32 ALTMAP kernel, or simply caching tables, could plausibly erase the GPU's margin. The student's paper also notes that field width and sector tolerance s vary together, and that size runs were confounded by order and fresh calibration. Both points are correct and should stay. The 128 MiB reversal (GPU 0.71× of best CPU) has no explanation in the literature. Laptop-GPU PCIe limits and per-recovery buffer allocation (2.17 ms of alloc/free API time in the trace) are the obvious suspects, and the Nsight data the student already has points toward them.

## A novelty statement the student can defend

The student's paper already makes a commendably modest claim ("a reproducible implementation, bottleneck analysis, and evaluation on one CPU/GPU system, rather than a new code construction"). It undersells the two items the gPPM full text shows to be genuine gaps. A version that is accurate and examiner-proof:

> "We reimplement PPM/gPPM decoding for Sector–Disk codes (Li et al., ICPP 2015; TACO 2023) in C. We extend it in three ways the original leaves open. First, gPPM decodes the dependent remainder serially after its independent groups. We parallelize that remainder by splitting its data regions into symbol-aligned byte ranges, a standard data-parallel technique, and gain 1.20–1.86× at eight threads. Second, gPPM defines a multiply-to-XOR weight c in its cost model C = u + c·v but does not specify its value. We measure c per field and backend on the host, following the empirical weighting approach of Zhou and Tian (FAST 2019). Third, gPPM explicitly chose CPU threads over GPUs. To our knowledge we give the first CUDA decoder for SD codes and for gPPM-style partitioned recovery, mapping independent groups to CUDA streams. Our SIMD kernels re-implement established GF-Complete/ISA-L techniques; gPPM also used SIMD. Our controlled CPU/GPU comparison finds the GPU faster only for GF(2^32) at 32 MiB (1.25–1.39×). This agrees with prior fair-baseline studies, and we partly attribute it to our comparatively slow GF(2^32) CPU kernel."

Three phrasings should be avoided in the viva. "First SIMD gPPM" is false, because gPPM's experiments used Intel SIMD. "First hardware-calibrated cost model" is contradicted by Zhou & Tian. "GPU is better for wide fields" in general terms is not supported, because the CPU baseline for that field is known to be weak and field width is confounded with s.

## Conclusion

The full gPPM text changes the picture in the student's favour on two points and against it on one. The remainder parallelization and the measured c are now clearly filling holes in gPPM rather than re-tuning it. The SIMD work loses any claim to novelty, because gPPM ran on ISA-L/GF-Complete from the start. The project's centre of gravity is therefore the GPU port. Its value lies less in the kernels, which are standard, than in being the first empirical answer to gPPM's untested assertion that CPU threads were the better choice. That answer is "mostly yes, except at wide fields on mid-size stripes."

The most valuable next step is not more novelty but more fairness. The project's one positive GPU result coincides with its weakest CPU kernel, and its calibrated c is currently measuring that same weakness. Fixing GF(2^32) table reuse and rerunning both the selector ablation and the CPU/GPU comparison would settle whether the student has found a real field-width crossover or a kernel artifact. Either answer is publishable as an honest workshop- or course-level result.
